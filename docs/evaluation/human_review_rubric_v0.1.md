# Mini Opportunity Miner 人工评估标准 v0.1

状态：评估方案草案，尚未执行。日期：2026-09-19。

## 1. 这次要证明什么

检验 Agent 能否从简短研究需求中找到相关来源、生成有原始 Issue 支撑的痛点机会卡，并在证据不足或请求失败时正确处理。GitHub 证据可以支持痛点存在，不能证明市场规模、付费意愿或商业成功。

配套工作簿含 20 条拟定需求：笔记工具、客服、RAG、浏览器 Agent 各 5 条；每领域 3 条调试、2 条独立验收，共 12/8。全部结果留空。它们是拟定测试输入，不是历史真实运行输入，也不是已经通过的案例。

## 2. 使用顺序

1. 确认“测试需求”中的输入和判断边界，允许在首次运行前修改。冻结后记录日期和文件版本。
2. 先用 2 条调试案例校准判定标准。第一次按标准标注；间隔至少一天盲看同一批材料复核，记录分歧和裁决。只有一个人审核时，称“人工标注/复核”，不称专家评审或多人一致率。
3. 用 12 条调试需求定位问题；不能用 8 条验收需求反复调参。若验收集已用于修改方案，应转为调试集并补充新的验收需求。
4. 固定一个基线版本和一个待评版本。同一需求各运行一次，填入两个独立运行槽位。重复执行保留全部记录，事前确定重复次数和汇总方式，不挑最好的一次。
5. 来源审核每次取最终候选来源的前 5 个；机会卡审核该次全部卡。填完审核人、原始链接/快照及判定依据后，工作簿才认可该条审核。
6. 流程故障注入单独执行，不能把 mock/离线通过率算成线上检索质量。

最低可行起步：先完成 2 条调试案例的运行与标注，不必一次跑完 40 次。

## 3. 公平比较与材料

每个运行槽位填写唯一 run_id、配置快照路径、产物目录。配置快照应保存：代码 commit、未提交差异的备份路径、scoring_version、模型/模型版本、提示词版本、执行时间、运行模式（live / snapshot / mock）、原始输入、批准内容、预算、最大扩展次数、请求/耗时/成本（若采集）、采样参数及缓存设置。不要把密钥写入评估材料。

离线比较使用同一 GitHub 数据快照，只验证排序/流程；在线比较尽量在相近时间、同一请求预算下进行，记录 GitHub 数据和网络变化。不同模式不混合平均。审批方式须一致，人工修改和接管必须记录。

来源阶段口径固定为 `github_evidence_sources.json` 中最终候选 sources/candidates 的原始排序，且在人工批准之前。不要只选获批来源，不要用 repo-stage repository_rankings 替代此口径。仓库预排序的问题另记为 badcase；两种阶段不能混在同一个 P@5 中。

保留原始 trace、diagnosis、intake、search plan、来源列表、Issue 内容快照、机会卡及报告。具体文件名以该 run 的实际产物为准。原始链接失效时使用保留的快照，不凭印象补证据。

## 4. 来源相关性判定

先读冻结的需求边界，再检查候选仓库名称、描述、README/产品功能、topics，以及实际引用内容。star 低不等于不相关；star 高不等于相关。repo viability 与相关性分别看，不能用 Agent 自己的分数当人工标签。

| 标签 | 可操作标准 | 严格相关分子 |
| --- | --- | --- |
| 相关 | 仓库核心功能直接服务所需领域或工作流，能指出明确功能证据 | 1 |
| 边界相关 | 是相邻领域或通用框架，仅有潜在用途，无法确认核心工作流 | 0 |
| 不相关 | 明显不属于领域；课程笔记、资源清单等不满足产品来源条件 | 0 |
| 无法判断 | 必要材料缺失或不可访问，不能作肯定判断 | 0 |

四种均为已完成判定；“无法判断”单独记录原因，不能删除该来源以提高分数。空标签是待审核，不计已审核。审核理由须包含功能证据或不满足哪条边界，不能只写“符合”。

例（仅为判定示例）：笔记同步需求下，提供跨设备笔记同步的产品是相关；个人课程笔记仓库不相关；通用向量数据库对笔记产品通常只有边界相关性。是否覆盖学生场景必须另有证据，不从笔记软件自动推断。

## 5. 机会卡证据判定

每张卡记录卡 ID、关键痛点主张、支持链接/快照、判定理由。必须检查全部关键痛点主张，而不只是其中最好支持的一句。一个链接可支持多张卡，但不能因此说有多个独立用户。

| 标签 | 可操作标准 | 严格支持分子 |
| --- | --- | --- |
| 完全支持 | 全部关键痛点能追溯到真实 Issue 原文；产品、人群、场景、问题描述一致，未夸大频率或影响 | 1 |
| 部分支持 | 只有部分痛点有证据，或将普通用户扩大为学生/企业等未经证实的人群 | 0 |
| 不支持 | 引用不相关、与原文相反、将请求功能当已证实损失，或无证据推出“普遍/高频” | 0 |
| 无法核验 | 缺少原文/快照，不能验证关键引用 | 0 |

主张“多位用户/反复出现”须有相应独立用户/事件证据；comments/reactions 数量不是独立用户数或痛点频率。已关闭 Issue 不能自动算仍未解决，须检查修复状态、替代方案和时间。机会方案与商业判断可作为待验证假设，但必须明确标注；不能由真实痛点直接宣称付费需求。

## 6. 指标与分母

| 指标 | 公式与使用限制 |
| --- | --- |
| 单次 Top-5 来源相关占比 | 人工“相关”数 / 实际返回的前 min(5, N) 个来源。少于 5 个按实际数计算，并报告数量；0 个时该指标不适用，不填 100% |
| 汇总来源相关占比 | 对审核完整且执行已结束的运行，相关数之和 / Top-5 实际来源数之和；这是 micro 汇总，不是逐运行平均 |
| 机会卡证据支持率 | 全部卡审核完整的运行中，“完全支持”卡数 / 全部已审核卡数；无卡时不适用 |
| 零来源运行数 | 执行已结束且最终候选数为 0 的次数；必须与相关占比同时报告 |
| 无卡运行数 | 执行已结束且实际生成卡数为 0 的次数；必须与证据支持率同时报告，不因无卡就视为完全支持 |
| 流程达标率 | 有记录、有审核人的通过场景数 / 已通过或未通过的场景数；未执行和阻塞单列，不计成功 |

分开报告：调试/验收、基线/待评、线上/离线。未运行不是失败；执行失败不是无需求；已结束的 partial 可能是正确行为，但不是机会发现成功。来源或卡审核未完成时，不把部分已审记录用于发布该运行的质量成绩。

工作簿显示质量指标对应的已审运行数和分子/分母。验收需两版本相同 8 条全部结束，且各个非零样本审核完整、对照条件核验一致后，才允许写正式前后对比。若某次没有来源或卡，保留该结果，报告覆盖情况；不能只比较两边有结果的案例而不披露筛选。

不计算全网召回率：没有完整真实相关集合。已知仓库名单的命中率只能称“已知来源覆盖率”，不能改名为全局 recall。固定小样本不支持“普遍提升”等泛化结论。

## 7. 流程判定标准

配套“流程验收”给出 12 类场景，每版本一条。需记录 fixture/输入、运行日志、实际状态和审核人。

- 通过：所有预期行为满足，并有产物/测试输出证明。
- 不通过：任一预期行为违反，例如批准后又阻断、覆盖人工编辑或证据不足仍虚构机会卡。
- 阻塞：环境/凭据/工具问题导致无法判定。修复后复测，但保留此次记录。
- 未执行：默认状态，不表示实现失败。

仓库阶段 viability 只允许使用仓库元数据，不允许使用尚未检索的真实 Issue 内容。`has_issues` 是功能开关；公开问题数量是先验，不等于已验证痛点。低 viability 不应自动删除；扩展后必须重新排序并按预算进入主流程。

## 8. 表格填法与边界

黄色为填写区，灰色为计算区。先填运行记录，再填关联审核。评估槽位是工作簿内部 ID，不是实际 run_id。来源每槽位预留 5 行；机会卡每槽位预留 10 行。超过 10 张时，复制整个模板并扩充审核行及公式引用范围后再统计，不能只挑 10 张。公式会提示数量不完整。

“候选来源数”填写最终列表去重后的总数，不是 API 搜索 total_count；“机会卡数”填写全部实际生成卡数。真实 0 要填数字 0，不留空。空白表示未获取数据。来源重复、卡 ID 重复、缺审核依据或审核人不会计为有效审核。

本模板不自动发布版本差异。比对配置、样本和失败原因后，再计算百分比差值，使用“提高 X 个百分点”。日期、链接、配置和运行日志需要人工核实；公式无法替代这部分审核。

## 9. 简历表达模板（未测前不可填成绩）

> 建立覆盖 4 类场景的 20 条需求评估集，按 12 条调试、8 条独立验收划分；制定来源相关性、机会卡证据支持与异常流程处理的人工判定标准。

上句只有在需求确认并完成标准建立后可用。“完成 20 条实测”要等实际执行结束。

> 在固定的 8 条验收需求、相同配置与请求预算下，Top-5 来源相关占比由 A/B 提升至 C/D；零来源运行由 E/8 变为 F/8，机会卡关键痛点证据支持率为 G/H（人工核验）。

所有字母均为待填占位，不是本项目已有成绩。如果结果没有提升，应如实报告基线数据和已定位的 badcase，不反向修改标准。
